# iOS 16 管理恢复与隐藏验证规格

## 问题

iPhone 13 Pro / iOS 16.3 上，1.0.4 提交隐藏后，小红书仍可从桌面和搜索找到。再次进入计算器或管理页时可能卡住，导致无法解除限制。管理列表滑动时也不够流畅。真机报告确认 App 被退出看门狗终止，且主线程当时在等待系统消息。

## 方案

优先保证用户能打开计算器、进入管理页、查看记录和导出日志。把 App 列表的展示从系统元数据查询中分离，将限制和存储操作放到单独的串行队列。以同一台设备的单 App 对照验证授权、上锁、隐藏和恢复，并根据实际系统结果决定后续隐藏方案。

## 用户故事

1. 作为使用者，我想在已提交隐藏的情况下仍能打开计算器，以便继续使用或恢复 App。
2. 作为使用者，我想重进管理页就看到保存的条目，以便马上确认本地记录。
3. 作为使用者，我想看到系统实际返回的授权状态，以便确认是否需要重新授权。
4. 作为使用者，我想在系统服务较慢时继续滚动、返回和导出日志，以便把问题交给开发者定位。
5. 作为使用者，我想知道限制操作是否仍在等待系统，以便避免重复点按。
6. 作为使用者，我想分别验证上锁和隐藏，以便区分限制页、桌面图标和搜索结果的行为。
7. 作为使用者，我想逐个恢复 App，以便只解除我指定的限制。
8. 作为使用者，我想从管理页恢复全部，以便快速回到计算器。
9. 作为使用者，我想保存备注名称，以便下次快速认出系统选择器里选过的 App。
10. 作为使用者，我想在一个紧凑的列表里完成状态切换，以便更快管理多个 App。
11. 作为使用者，我想把问题日志导出为文本，以便在没有本地 Mac 的情况下提供证据。
12. 作为使用者，我想在覆盖更新后保留原有选择、模式和 PIN，以便继续管理之前设置的 App。

## 实现决策

- 保持固定应用身份、Keychain 和原有命名 store。旧记录兼容，备注可选。未填写备注时显示编号。备注写入只改本地记录。
- 系统选择器继续负责选择 App。列表用本地文字、SF Symbols 和稳定条目 ID。状态菜单保留正常、上锁、隐藏，日志放入可展开区域。
- 文件加载和限制操作由同一后台队列串行执行。系统调用慢时保留退出和日志入口，待完成后更新请求状态。同一时刻只提交一个操作。恢复与退出后不从缓存自动重施加。
- 授权、shield 写入和 blocked 写入分别记录开始和结束。日志只保留操作阶段、系统错误与数量。界面把保存模式称为请求状态。
- 真机按「正常 → 上锁 → 正常 → 隐藏 → 正常」记录。每一步检查图标、搜索、实际启动和系统限制页；再冷启动计算器，确认授权状态和恢复路径。

## 测试决策

- 以管理页和策略控制器的外部行为为测试入口。已有核心用例覆盖切换、恢复和隔离；补充旧隐藏记录和备注迁移，断言加载、备注与重进均不会调用限制写入。
- 后续模拟器回归通过旧记录和受控延迟验证进入、滚动、退出、日志和恢复的可达性。SwiftUI 状态更新和列表布局通过实际界面操作检查。
- 同一台 iOS 16.3 真机独立验收授权、shield 限制页、桌面/搜索隐藏和恢复。使用相同条目和安装身份复测。滚动用固定条目数和相同手势记录卡顿，设备可用时用 Instruments 的 SwiftUI 和 Hangs 模板定位。
